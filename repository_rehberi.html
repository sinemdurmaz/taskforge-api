Temel Kural: API Router veya Servis katmanı asla doğrudan SQL sorgusu yazmaz veya session.exec(select(...)) ile uğraşmaz. Veri istemek için tek muhatap Repository'dir.

⚖️ Repository Deseni Olmadan vs. Olduğunda

Bu deseni kullanmak bize ne kazandırır? Spagetti kod ile temiz mimari arasındaki fark:

❌ Repository Kullanılmadığında ✅ Repository Pattern İle
Her endpoint'in içinde session.exec(select(...)) sorguları kopyalanıp yapıştırılır (Kod Tekrarı). Sorgular tek bir yerde toplanır. Bir sorgu değiştiğinde yalnızca o metot güncellenir (DRY Prensibi).
Birim test (Unit Test) yazarken gerçek bir veritabanı bağlamak zorunlu hale gelir; testler çok yavaşlar. Repository soyut bir arayüz olduğu için testlerde sahte (Mock / In-Memory) repository enjekte edilip milisaniyede test koşulur.
Veritabanı teknolojisini değiştirmek (örn. SQLite'tan MongoDB veya DynamoDB'ye geçmek) tüm projeyi yeniden yazmayı gerektirir. Yalnızca ilgili Repository sınıfının içi değiştirilir. Servisler ve API endpoint'leri hiçbir şey fark etmeden çalışmaya devam eder.

🧬 Generic Programlama: BaseRepository[T]

Her model için tek tek get(), create(), update(), delete() yazmak yerine Python'ın Generic tipleriyle tek bir temel depo sınıfı inşa ediyoruz:

from typing import Generic, TypeVar, Type, Sequence
from sqlmodel import Session, select, SQLModel

# ModelType: SQLModel'den türeyen herhangi bir varlık olabilir (User, Task, Project vb.)
ModelType = TypeVar("ModelType", bound=SQLModel)

class BaseRepository(Generic[ModelType]):
    def __init__(self, model: Type[ModelType], session: Session):
        self.model = model
        self.session = session

    def get(self, id: int) -> ModelType | None:
        return self.session.get(self.model, id)

    def create(self, entity: ModelType) -> ModelType:
        self.session.add(entity)
        self.session.commit()
        self.session.refresh(entity)
        return entity

Artık UserRepository veya TaskRepository yazdığımızda tüm bu CRUD fonksiyonları otomatik olarak gelir; sadece modele özel sorguları (örn: get_by_email veya get_project_tasks) eklememiz yeterlidir!

📐 Bu Katmanda SOLID ve OOP Kuralları

SOLID: Dependency Inversion (D)

Soyutlamalara Bağımlılık

Üst katman olan Servis katmanı, alt katman olan SQLite oturumunun iç mekanizmasına değil, Repository sınıfının sunduğu soyut metotlara (get(), create()) güvenir.

SOLID: Single Responsibility (S)

Yalnızca Veri İletişimi

Repository'ler parola doğrulaması yapmaz, JWT üretmez, e-posta yollamaz. Tek işleri: Veritabanından veri almak ve veritabanına veri yazmaktır.

OOP: Kalıtım (Inheritance)

Kod Tekrarına Son

class TaskRepository(BaseRepository[Task]): tanımlamasıyla tüm temel CRUD yetenekleri anında miras alınır.

SOLID: Open / Closed (O)

Genişletilebilir Yapı

Yeni bir tablo eklendiğinde var olan BaseRepository koduna dokunmadan yeni bir alt sınıf açarak sistemi kolayca genişletebiliriz.
